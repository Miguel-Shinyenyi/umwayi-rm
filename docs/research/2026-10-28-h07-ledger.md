# 2026-10-28: H-07 ledger design

Date: 2026-10-28. Source: written record of H-07 design decisions (no prior response existed to quote). Purpose: research data for measurable outcomes. Status: notes, not results.

## Decisions

1. One LedgerStore interface, two implementations. Memory runs the domain locally with no database. Postgres carries the real persistence. No HTTP in H-07; routes arrive with H-09 and H-10.
2. One conformance suite defines ledger behavior: create round trip, idempotent approval, reject lifecycle, non-entry refusal, cross-group 403, validation rejects, list filters. Both stores run it. The pg file adds the trigger test. Skips without a database are stated, never green.
3. Append-only has two layers. Code offers no update or delete path for entries. A database trigger rejects UPDATE and DELETE loudly so a future bug cannot silently rewrite history.
4. Idempotent approval is transactional. The proposal row locks, repeat approval returns the existing entry with an already flag, and decided proposals refuse with 409. entries.proposal_id (unique) links entry to proposal and is now in the contract.
5. Access resolves on every call. Each method takes the treasurer token first and denies cross-group use with 403. Tokens are random 32-byte hex, one per group.
6. Migration runner is plain SQL files in order with a tracking table. No ORM. pg is the only new runtime dep.

## How this is tested

Memory suite runs locally. The pg suite plus trigger test run in CI against real Postgres. H-07 acceptance is both suites green.
